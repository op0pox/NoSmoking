## 1. 설계 원칙

프로젝트 전체를 관통하는 원칙 3가지. 아래 개별 기능의 "왜 이렇게 만들었나"는 대부분 이 중
하나로 설명된다.

| 원칙 | 내용 | 근거 |
|---|---|---|
| **영상 무저장** | 프레임은 추론 직후 메모리에서 폐기. 저장·외부 전송·녹화 코드를 만들지 않는다. 녹음(오디오 입력)도 만들지 않는다 | 개인정보보호법 제25조(고정형 영상정보처리기기) 대응, 프로젝트 차별점 |
| **정밀도 우선** | 비흡연자에게 방송이 나가는 오탐이 최악의 실패. 미탐(놓침)은 허용 | 목적이 계도이지 단속·처벌이 아님 |
| **표준 모델 구조 유지** | YOLOv8n 계열 네트워크 구조·레이어를 바꾸지 않는다. 성능 개선은 데이터·증강·임계값으로 | 향후 하드웨어 확장 시 컴파일 호환성 확보 |

## 2. 시스템 구성

```
[입력]                  [감지 파이프라인 — 노트북]                                   [출력]
웹캠(실시간)   ─┐                                                                ┌─ 화면 오버레이 (OpenCV 창)  ✅
               ├─▶ 사람+포즈 → 1차 게이트(모션) → 2차 확인(담배/연기) → 시간 필터 ─┤
영상 파일      ─┘                                                                └─ 안내 음성 (노트북 스피커) ✅

[개발·검증 도구]
- 이벤트 단위 평가 도구 (python -m eval.run)          ✅  — 6장
- 웹 데모 화면 (React + FastAPI, localhost 전용)      📋  — 7장
- 서버·DB·대시보드                                    ❓  — 9장
```

입력 소스는 주입 가능하게 설계되어 있어, 같은 파이프라인이 웹캠과 영상 파일 양쪽에서 그대로
돈다(`--source`).

## 3. 감지 파이프라인 ✅

```
사람+포즈 감지 → 1차 게이트(손-입 모션) → 2차 확인(담배/연기 객체) → 시간 필터 → 음성 안내
```

모든 판정 상태는 **사람(track id)별로 독립**이다. 튜닝 대상 상수는 각 파일 상단에 모여 있다.

다섯 단계는 `edge/pipeline.py`의 `SmokingPipeline`이 하나로 묶는다. 프레임과 시각을 넣으면
사람별 상태와 이번 프레임의 이벤트(이벤트 확정, 안내 방송)를 돌려주고, 화면은 그리지 않는다.
실시간 실행(`edge/motion_detector.py`)과 평가 도구(`eval/`)가 같은 파이프라인을 쓰고, 웹
데모(7장)도 이것을 재사용한다 (#44).

### 3.1 사람 + 포즈 감지 ✅

**기능**: YOLOv8n-pose로 프레임마다 사람 박스와 COCO 17 keypoints를 다중 인물로 추출하고,
ByteTrack으로 사람별 track id를 부여해 프레임 간 동일 인물을 유지한다. 추론 해상도는
`--pose-imgsz`로 조정한다(기본 640).

**왜 이렇게 했나**:
- 별도의 사람 감지 모델을 두지 않았다 — 포즈 모델이 사람 박스를 함께 출력하므로 모델 하나를
  아낄 수 있다.
- MediaPipe Pose가 아니라 YOLOv8n-pose를 썼다 — MediaPipe는 단일 인물용이라 여러 명이
  동시에 있는 장면에 맞지 않는다.
- 트래커를 ByteTrack으로 명시적으로 고정했다 — 일부 ultralytics 버전의 기본 트래커는 새 track
  생성 임계값이 높아(0.7 등) 웹캠의 일반적인 포즈 신뢰도로는 track id가 아예 배정되지 않았다.

**확인된 한계** (2026-10-26 test4·test5 진단, 6.3 참고):
- 사람이 많고 서로 가려지는 장면에서 사람을 놓친다 — 7명 중 프레임당 3명(640) / 5명(1280)만 검출.
- track id가 자주 바뀐다 — 5~7명인 영상에서 track id가 18~26개 생성됐다. id가 바뀌면 그 사람의
  puff 카운트가 0부터 다시 시작되어 모션 누적이 끊긴다.
- 포즈 해상도(640 / 1280)에 따라 판정 결과가 크게 달라진다. 사람이 화면 높이의 30~40%로
  찍힌 영상에서도 640에서는 얼굴 근처 손목 위치가 부정확했다.

**구현**: `edge/pipeline.py` — `SmokingPipeline`

### 3.2 1차 게이트 — 손-입 반복 모션 감지 ✅

**기능**: 손목과 입(추정) 사이 거리를 어깨너비로 정규화한다. 이 거리가 임계값 미만으로
1~6초 유지됐다가 벌어지면 puff(한 모금) 1회로 카운트한다. 60초 윈도 안에 puff가 3회 이상이면
그 사람을 `SMOKING_SUSPECTED`로 전환한다.

**사람별 상태**

| 상태 | 조건 |
|---|---|
| `IDLE` | 기본 |
| `PUFF` | 손이 입 근처에 있는 중(유지 시간 측정 중) |
| `SMOKING_SUSPECTED` | 최근 60초 안에 puff 3회 이상. 윈도에서 puff가 빠져 3회 미만이 되면 해제 |

**주요 파라미터**

| 상수 | 값 | 의미 |
|---|---|---|
| `NEAR_THRESHOLD` | 0.6 | 정규화 거리가 이 값 미만이면 "입 근처" |
| `MOUTH_OFFSET_RATIO` | 0.08 | 코 좌표를 어깨너비 × 이 비율만큼 아래로 내려 입 위치로 사용 |
| `MIN_HOLD_SEC` / `MAX_HOLD_SEC` | 1.0 / 6.0초 | 이 범위로 유지돼야 puff 인정. 6초 초과는 통화 등 장시간 접촉으로 보고 무효 |
| `WINDOW_SEC` / `MIN_PUFFS` | 60초 / 3회 | puff 누적 윈도와 의심 전환 기준 |
| `KEYPOINT_CONF_THRESHOLD` | 0.5 | 코·어깨 keypoint 최소 신뢰도 |
| `WRIST_CONF_THRESHOLD` | 0.15 | 손목 전용 최소 신뢰도 (손목은 움직이는 중에도 신뢰도가 낮게 나옴) |
| `NEAR_EXIT_GRACE_SEC` | 0.3초 | 거리값이 한두 프레임 튀는 것을 puff 종료로 보지 않는 유예 |
| `WRIST_OCCLUSION_GRACE_SEC` | 3.0초 | 손이 얼굴을 가려 손목만 안 보일 때 진행 중인 puff를 유지하는 유예 |
| `POSE_LOST_GRACE_SEC` | 0.5초 | 사람 전체를 잠깐 놓쳤을 때의 유예 |
| `STALE_TRACK_TIMEOUT_SEC` | 5.0초 | 이 시간 이상 안 보이면 해당 사람의 상태를 폐기 |

**왜 이렇게 했나**:
- 학습이 필요 없는 규칙 기반이라 라벨링 데이터가 부족한 초기에도 바로 쓸 수 있었다.
- 손-입 반복 동작은 연초·전자담배 공통이라 기기 종류를 가리지 않는다.
- COCO keypoints에 입이 없어 코 좌표를 보정해 쓴다.
- 손가락 사이에 담배를 끼우는 자세는 손목-입 사이에 손 길이만큼 거리가 더 있어 실측 정규화
  거리가 0.44~0.6대로 나왔다(2026-09-14 실측). 그래서 임계값을 0.35가 아니라 0.6으로 잡았다.
  1차 게이트는 재현율 우선으로 넉넉히 잡고, 정밀도는 2차 확인과 시간 필터에서 확보한다.

**확인된 한계**:
- **마시기·통화와 구분하지 못한다** — 물 마시는 동작도 puff 3회로 인정됐다(#39). 모션은
  흡연의 필요조건일 뿐 구분 근거가 아니다.
- **손을 입 근처에 계속 들고 피우면 잡지 못한다** — 손을 내리지 않아 puff가 끝나지 않고,
  6초를 넘으면 무효 처리된다. 통화 오탐을 막는 `MAX_HOLD_SEC` 규칙의 대가로, 정밀도 우선
  기조에서 허용하는 미탐이다. 이런 경우는 2차 확인 경로(3.3)로만 잡힌다.
- **저프레임 영상에 약하다** — 3fps에서는 1초 유지를 인정받으려면 3프레임 연속으로 기준 아래여야
  하고, 이탈 유예(0.3초)가 프레임 간격(0.33초)보다 짧아 사실상 꺼진다.

**구현**: `edge/motion_gate.py` — `SmokingMotionDetector` 클래스

### 3.3 2차 확인 — 담배/연기 객체 감지 ✅ 🔧

**기능**: 사람 bbox를 크롭해 커스텀 YOLOv8n(cigarette=0, smoke=1)을 돌리고, 모션과 객체
신호를 조합해 프레임별 combined 점수를 낸다. combined가 0.5 이상이면 그 프레임을 "흡연"으로
판정해 시간 필터(3.4)에 넘긴다.

**실행 조건** (#28)

| 사람 상태 | 2차 확인 실행 |
|---|---|
| `SMOKING_SUSPECTED` | 매 프레임 |
| 그 외 | `OBJECT_CHECK_INTERVAL_SEC`(1초) 주기 |

모션 3회를 다 채우지 못해도 담배·연기가 여러 번 보이면 잡을 기회를 주되, 상시 실행은 피해서
연산을 아끼기 위함이다.

**combined 점수** — 아래 네 값 중 최댓값

| 경로 | 계산 | 의도 |
|---|---|---|
| 담배 + 연기 | √(cig × smoke) | 모션이 없어도, 담배와 연기가 5초(`CIG_SMOKE_COOCCURRENCE_WINDOW_SEC`) 이내에 각각 검출되면 짝으로 인정 |
| 담배 + 모션 | √(cig × motion) | motion = min(puff 수 / 3, 1) |
| 연기 + 모션 | √(smoke × motion) | 〃 |
| 고신뢰도 바이패스 | 신뢰도 그대로 | cig 또는 smoke ≥ 0.75이면서, puff ≥ 2회이고 최근 10초 안에 고신뢰도 검출이 2회 이상일 때만 (#30, #35) |

- 두 신호의 기하평균이라 **하나라도 0이면 0**이다. 단일 신호로는 점수가 오르지 않는다.
- 객체 검출이 프레임마다 깜빡이는 것을 완화하려고, 모션과 짝지을 때는 최근 1.5초
  (`OBJECT_SIGNAL_HOLD_SEC`) 안의 마지막 검출값을 대신 쓴다.

**왜 이렇게 했나**:
- 모션만으로는 통화·음료·안경 고쳐 쓰기와 구분되지 않는다. 실제 담배·연기가 있는지 확인해야
  정밀도가 확보된다.
- 담배 같은 작은 물체는 전체 프레임에서는 해상도가 부족해 거의 검출되지 않았다. 사람 영역만
  크롭하자 검출률이 크게 개선됐다.
- 고신뢰도 단일 검출을 인정하되 지속성·최소 모션 조건을 붙인 이유: v2 모델이 배경 물체를
  0.88로 오인한 사례가 있어 단일 프레임 신뢰도만으로는 안전하지 않았다.

**주요 파라미터**: `OBJECT_CHECK_INTERVAL_SEC`(1.0초), `COMBINED_CONFIRM_THRESHOLD`(0.5),
`OBJECT_SIGNAL_HOLD_SEC`(1.5초), `HIGH_CONFIDENCE_THRESHOLD`(0.75), `HIGH_CONF_MIN_PUFFS`(2),
`HIGH_CONF_SUSTAIN_WINDOW_SEC`(10초), `HIGH_CONF_SUSTAIN_COUNT`(2),
`CIG_SMOKE_COOCCURRENCE_WINDOW_SEC`(5초)

**확인된 한계와 개선 검토** → 8장
- 물 마시는 영상에서 오탐 (#39)
- 크롭에 배경이 섞여 오검출 (#34)
- 1초 주기 샘플링이 순간적인 고신뢰도 검출을 건너뜀 (#32)

**구현**: `edge/cigarette_detector.py` — `CigaretteDetector` 클래스, 점수 계산은
`edge/pipeline.py`

### 3.4 시간 필터 ✅

**기능**: 사람별로 최근 10초 슬라이딩 윈도 안에서 "흡연" 판정 프레임 비율이 60% 이상일 때만
이벤트를 확정한다.
- 관측 시작 후 10초가 지나기 전에는 확정되지 않는다 (표본 1~2개로 순간 확정되는 것 방지).
- 판정 입력이 10초 이상 끊기면 관측을 새로 시작한다.
- 확정 상태는 래칭되지 않는다 — 비율이 떨어지면 미확정으로 돌아간다. 방송 여부 판단은 음성
  상태 머신(3.5)의 책임이다.

**왜 이렇게 했나**: 한 프레임의 순간적인 오탐으로 이벤트가 확정되면 정밀도 우선 원칙에
어긋난다. 지속적인 신호일 때만 확정하도록 시간 축에서 한 번 더 거른다.

**참고**: 2차 확인은 1초 주기로 돌기 때문에, 의심 상태가 아닌 사람은 10초 윈도에 표본이 약 10개다.
표본 수에 따라 비율이 크게 흔들린다(8.4 실험 참고).

**구현**: `edge/event_filter.py` — `EventTimeFilter` 클래스
(`EVENT_WINDOW_SEC` 10초, `EVENT_CONFIRM_RATIO` 0.6)

### 3.5 음성 안내 상태 머신 ✅

**기능**: 사람별로 동작한다.

```
IDLE ──(이벤트 확정)──▶ 1차 안내 재생 → FIRST_ANNOUNCED
FIRST_ANNOUNCED ──(30초 시점에 여전히 확정)──▶ 2차 안내 재생 → COOLDOWN
FIRST_ANNOUNCED ──(30초 시점에 미확정)──▶ COOLDOWN (방송 없음)
COOLDOWN ──(60초 경과)──▶ IDLE      * 쿨다운 중 재확정은 무시
```

- 1차: 완곡한 안내 mp3 (`--first-mp3`, 기본 `assets/audio/first_announce.mp3`)
- 2차: 법적 고지 포함 안내 mp3 (`--second-mp3`, 기본 `assets/audio/second_announce.mp3`)
- mp3 파일이 없으면 경고를 출력하고, 재생 없이 로그만 남긴다.
- 상수: `SECOND_ANNOUNCE_WINDOW_SEC`(30초), `COOLDOWN_SEC`(60초)

**왜 이렇게 했나**:
- 목적이 계도라서 처음부터 강한 경고를 주지 않고 완곡한 안내 → (지속 시) 법적 고지 순으로
  단계를 나눴다.
- 실시간 TTS와 마이크를 쓰지 않는다 — 사전 녹음 mp3만 재생한다. 오디오 입력은 법적으로 금지된
  영역이라 설계에서 원천 배제했다.
- 별도 오디오 라이브러리 없이 OS 기본 플레이어(macOS `afplay`, Linux `mpg123`)를 논블로킹
  subprocess로 실행한다 — 의존성을 가볍게 유지하기 위함.

**구현**: `edge/voice_announcer.py` — `VoiceAnnouncer` 클래스

## 4. 실행 방법과 현재 화면 ✅

### 4.1 실행 옵션

```bash
source NS-venv/bin/activate
python edge/motion_detector.py                                       # 웹캠
python edge/motion_detector.py --camera 1                            # 다른 카메라 (맥 연속성 카메라 회피)
python edge/motion_detector.py --source test_videos/xxx.mp4          # 영상 파일
python edge/motion_detector.py --source test_videos/xxx.mp4 --pose-imgsz 1280   # 원거리 영상
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--source` | `webcam` | `webcam` 또는 영상 파일 경로 |
| `--camera` | 0 | 웹캠 인덱스 |
| `--model` | `yolov8n-pose.pt` | 포즈 모델 가중치 |
| `--cigarette-model` | `cigarette-v4-best.pt` | 2차 확인 모델 가중치 |
| `--first-mp3` / `--second-mp3` | `assets/audio/...` | 1차·2차 안내 음성 |
| `--pose-imgsz` | 640 | 포즈 추론 해상도. 사람이 작게 나오는 영상은 1280~1920 |

- **영상 파일 모드**: 시간 기준을 영상 재생 위치(`CAP_PROP_POS_MSEC`)로 잡아, 처리 속도와
  무관하게 시간 임계값이 영상 속 실제 경과 시간과 맞는다. 끝까지 재생하면 사람별 결과 요약
  (최종 상태, puff 수, 이벤트 확정 여부)을 출력하고 종료한다.
  - 요약에는 종료 시점에 남아 있는 사람만 나오고, 확정 여부도 종료 시점 기준이다. 중간에
    확정됐다가 사라진 사람은 요약에 보이지 않는다.
- **웹캠 모드**: 좌우 반전(거울 모드)으로 표시한다.
- **왜 영상 모드를 앞당겼나**: 오탐 튜닝을 하려면 같은 시나리오를 반복 테스트해야 하는데,
  매번 동작을 재연하는 건 비효율적이다.
- **왜 해상도 옵션을 넣었나**: 원거리 테스트 영상에서 흡연 동작이 전혀 감지되지 않았는데,
  원인이 모델·임계값이 아니라 추론 해상도였다. 640은 1920×1080을 3배 가까이 축소해 보는 셈이라
  멀리 있는 사람의 손목 정보가 거의 사라졌다.

### 4.2 화면 구성 (OpenCV 창)

프레임은 화면 표시에만 쓰이고 저장되지 않는다. 화면은 모든 사람의 판정을 끝낸 뒤에 그린다 —
예전에는 판정 도중에 그려서 앞사람의 박스·스켈레톤이 뒷사람의 2차 확인 크롭에 섞여 들어갔다(#44에서 수정).

| 요소 | 내용 |
|---|---|
| 스켈레톤 | 사람별 색으로 관절과 연결선 표시 |
| 입 추정점 · 손목-입 연결선 | 판정 기준점(주황 점)과 손목까지의 선(노랑) |
| 상태 배지 | `#id 상태 d=거리 puff=횟수 2nd(cig= smoke= combined=) [판정비율/10s] 🔔EVENT 방송:상태`. 배경색: 이벤트 확정(진한 빨강) / 흡연 의심(빨강) / PUFF(주황) / IDLE(회색) |
| 객체 박스 | 이번 프레임에 실제 검출된 것만 표시. cigarette(빨강), smoke(파랑 계열) |
| 상단 정보 | FPS, 인원 수, 전체 puff 수 |
| 하단 그래프 | 최근 60초 정규화 거리 파형(사람별 색) + `NEAR_THRESHOLD` 기준선 |
| 키 조작 | `q` 종료, `r` 전체 상태 리셋 (창을 클릭해 포커스를 준 뒤) |

## 5. 모델·데이터

### 5.1 클래스 정의 ✅

| ID | 클래스 | 포함 |
|---|---|---|
| 0 | `cigarette` | 일반 담배 + 전자담배 기기 |
| 1 | `smoke` | 담배 연기 + 전자담배 에어로졸 |

**왜 통합했나**: 대상 객체가 약 10~30px로 관측되어 담배와 전자담배를 안정적으로 구분하기
어렵고, 목표도 기기 분류가 아니라 흡연 여부 판단이다. 사람·손·얼굴·흡연 행동은 라벨링하지
않는다(포즈 모델과 규칙이 담당). 상세 라벨링 기준은 이슈 #1.

### 5.2 모델 버전 이력

| 버전 | 가중치 파일 | 데이터 | val 결과 | 상태 |
|---|---|---|---|---|
| v1 | `cigarette-v1-best.pt` | 재라벨링 중 스냅샷, 약 200장 | mAP50 약 0.3, precision 변동 큼 | 폐기 |
| v2 | `cigarette-v2-best.pt` | `No-smoking-project-2` | P 0.394, R 0.384, mAP50 0.355, mAP50-95 0.195 | 폐기 |
| v4 | `cigarette-v4-best.pt` | `No-smoking-project-4` (라벨링 버전 4) | P 0.830, R 0.813, mAP50 0.801, mAP50-95 0.549 | 이전 기본값 (#37) |
| v5 | `cigarette-v5-best.pt` | `No-smoking-project-5` (마시는 장면 부정 샘플 약 200장 포함) | P 0.902, R 0.746, mAP50 0.843, mAP50-95 0.539 | **현재 기본값** (#42) |

- 전부 표준 YOLOv8n, imgsz 640, 100 에포크. val 수치는 가중치 파일에 저장된 값이다.
- 버전마다 val 세트가 달라 val 수치끼리 직접 비교하기는 어렵다. 버전 비교는 평가 도구(6장)로 한다.
- v4 학습 곡선: train·val loss가 함께 감소해 과적합 신호는 없다. val loss는 60 에포크 이후
  거의 평탄해 에포크를 늘려도 이득은 작을 것으로 보이며, 개선은 데이터 쪽에서 찾는다.
- val 수치는 두 클래스 평균이고, F1 최대 지점 기준이다. 정밀도 우선이라 실제로 쓰는 신뢰도
  임계값은 더 높을 수 있다.

**모델 교체 절차**: 가중치를 `cigarette-vN-best.pt`로 저장 → 이슈·브랜치 생성 →
`--cigarette-model` 기본값 변경 → 같은 평가 영상으로 이전 버전과 비교(6장).

### 5.3 데이터 운영 규칙 ✅

- **부정 샘플 확보**: 음료 마시기, 통화, 휴대전화를 얼굴 가까이 든 사람, 담배와 비슷한 소품(펜
  등)을 라벨 없이 포함한다. 정밀도 우선 원칙과 직결된다.
- **자체 촬영 병행**: 공개 데이터셋과 실제 촬영 환경의 도메인 차이가 실측으로 확인됐다. 같은
  모델도 촬영 거리에 따라 감지율이 크게 달라진다.
- **train/val 분리는 촬영 세션(영상) 단위로** 한다. 프레임 단위로 섞으면 성능이 부풀려진다.
- **커밋 금지**: 데이터셋(이미지·영상·라벨), 모델 가중치(`.pt`/`.onnx`/`.hef`), `runs/`.
  가중치는 저장소 밖(GitHub Release 등)으로 공유한다.

## 6. 정확도 평가

### 6.1 이벤트 단위 평가 도구 ✅

**기능**: `eval/labels.csv`에 적힌 영상마다 파이프라인을 화면 없이 끝까지 돌리고, 정답과 비교해
표로 출력한다. 영상·프레임은 저장하지 않고 숫자만 낸다 (#44).

```bash
python -m eval.run                                                       # 기본: v5, 포즈 640
python -m eval.run --weights cigarette-v4-best.pt cigarette-v5-best.pt   # 모델 비교
python -m eval.run --pose-imgsz 640 1280                                 # 포즈 해상도 비교
python -m eval.run --set pipeline.OBJECT_CHECK_INTERVAL_SEC=0.2          # 상수 바꿔서 실행
python -m eval.run --include-reference --out eval/results/v5.md          # 참고 영상 포함, 파일 저장
```

**출력**: 설정(가중치 × 포즈 해상도)별 요약 표, 함정 종류별 오탐, 영상별 결과(판정, 확정 수,
첫 확정·첫 방송 시각, 최고 판정 비율, 지연)

**정답 라벨 파일** (`eval/labels.csv`, 영상 1개당 1줄, 박스 라벨링 불필요)

| 열 | 내용 |
|---|---|
| `video` | `test_videos/` 안의 파일 이름 |
| `label` | `smoking` / `non_smoking` |
| `category` | 함정 종류(`drink`, `coffee`, `phone` …) 또는 `smoking` |
| `smoke_start_sec`, `smoke_end_sec` | 흡연 구간(초). 비우면 영상 전체. 지연 계산에는 시작 시각이 필요 |
| `split` | `main`(메인 수치) / `reference`(동작 조건 밖·모자이크 등 참고용) |
| `note` | 메모 |

**채점 기준**
- **장면 단위**: 흡연 영상은 흡연 구간 안에서 이벤트가 하나라도 확정되면 정탐, 아니면 미탐.
  함정 영상은 이벤트가 하나라도 확정되면 오탐. 방송은 구역 전체에 나가므로 계도 목적에서는
  이쪽이 핵심 지표다.
- **이벤트 정밀도**: 확정된 이벤트 중 흡연 구간 안에서 나온 비율. 시간 필터가 늦게 확정되는 것을
  감안해 구간 끝에 10초(`EVENT_WINDOW_SEC`) 여유를 준다.
- **지연**: 흡연 시작부터 첫 1차 안내까지(초).
- **처리 FPS**: 노트북에서 영상을 처리한 속도. 2차 확인이 1초 주기라 실시간보다 빠르게 나온다.
- 사람 단위 채점(흡연자 중 몇 명을 잡았나)은 아직 없다 — 사람별 정답 라벨이 필요하다.

**왜 필요한가**: 임계값을 강하게 하면 오탐은 줄지만 미탐이 늘 수 있다. 8장의 대책들은 오탐과
미탐을 함께 숫자로 확인하면서 적용해야 한다.

**목표**: 이벤트 정밀도 ≥ 95%, 재현율 ≥ 80%

### 6.2 평가 영상 세트 기준 📋

| 구분 | 수량 | 조건 |
|---|---|---|
| 흡연 | 5~10개 | 연초·전자담배 섞기, 사람·각도 다양하게, 10fps 이상, 1~2분 |
| 비흡연(함정) | 10개 이상 | 물·커피·통화·얼굴 만지기·하품 등 손이 입으로 가는 동작. 정밀도 우선이라 흡연보다 많이 |

- 영상 하나에 한 사람이 한 가지 행동만 하면 라벨이 단순해진다.
- **평가 영상은 학습에 쓰지 않는다** (촬영 세션 단위로 평가 전용 지정).
- 영상은 `test_videos/`에만 둔다(gitignore). 라벨 CSV는 커밋해도 된다.
- 흡연장 등에서 촬영해 팀원이 아닌 사람의 얼굴이 담긴 영상은 로컬 평가에만 쓰고, 학습 데이터·
  공유·발표 자료에는 쓰지 않는다.

### 6.3 현재 기준선 (v4, 2026-10-26)

영상 수가 적어 대략적인 기준선으로만 본다.

| 영상 | 내용 | 포즈 640 | 포즈 1280 |
|---|---|---|---|
| test1~3 | 흡연, **3fps**, 원거리(사람이 화면 높이의 약 11%) | 미확정 | 미확정 |
| test4 | 흡연장, 약 7명 대부분 흡연, 30fps | 1명 확정 | 미확정 |
| test5 | 흡연장, 약 5명 대부분 흡연, 30fps | 미확정 | 1명 확정 |
| drink | 물 마시기 1명, 30fps | **확정 (오탐, #39)** | — |

- test4·test5의 확정은 모두 모션이 아니라 담배 + 연기 경로로 이루어졌다.
- 평가 도구로 다시 잰 v4 / v5 비교 (포즈 640, 2026-10-27): v4는 drink 오탐 + test4 정탐,
  v5는 세 영상 모두 미확정(오탐 없음, 흡연도 놓침). 장면 정밀도 v4 50% / v5 —, 재현율 v4 50% / v5 0%.
- 얼굴 전체가 모자이크된 흡연 영상(E04_012, E04_043)은 v5로 640·1280 모두 미확정이었다. 입 주변이
  가려져 담배가 거의 검출되지 않아(2차 확인 중 3~5%) 참고 분류로만 둔다. 학습에도 쓰지 않는다.
- test1~3은 파이프라인 동작 조건(10fps 이상, 근거리) 밖이라 재현율 평가에 쓰기 어렵다.

## 7. 웹 데모 화면 📋

### 7.1 공통 조건

- **localhost 전용**: 같은 노트북 안에서만 동작한다. 영상이 기기 밖으로 나가지 않는다.
- **저장 없음**: 프레임과 영상을 디스크에 저장하지 않는다. 업로드한 영상은 처리하는 동안만 임시
  파일로 두고 처리 후 즉시 삭제한다.
- **구성**: React 프론트엔드 + FastAPI 백엔드. 백엔드는 기존 `edge/` 파이프라인 모듈을 그대로
  재사용한다.
- 서버 대시보드(9장)와는 분리한다 — 대시보드는 메타데이터만 보여준다.

### 7.2 실시간 페이지 📋

**목적**: 발표 시연. 웹캠 앞에서 흡연 동작과 함정 동작을 보여주고 판정 과정을 설명한다.

**화면 요소**
- 실시간 영상 + 오버레이: 스켈레톤, 손-입 거리, puff 수, 2차 확인 박스
- 사람별 판정 상태 표시: 정상 → 흡연 의심 → 이벤트 확정
- 이벤트 확정 시 안내 음성 재생
- "이 장치는 영상을 저장하지 않습니다" 등 프라이버시 설계를 보여주는 안내 영역

**동작**: 백엔드가 웹캠을 직접 읽어 파이프라인을 돌리고, 처리된 화면을 브라우저로 스트리밍한다.

### 7.3 영상 분석 페이지 📋

**목적**: 내부 검증·튜닝. 촬영한 영상을 넣고 언제, 왜 그렇게 판정했는지 확인한다.

**화면 요소**
- 영상 파일 업로드
- **타임라인 그래프**: 시간 축 위에 정규화 손-입 거리 곡선, `NEAR_THRESHOLD` 기준선, puff
  인정 시점, 이벤트 확정 구간
- **이벤트 목록**: 확정 시각, 대상 사람, 그때의 cig·smoke·combined 값
- **판정 근거 표시**: 어느 단계(모션 게이트 / 2차 확인 / 시간 필터)에서 걸렸는지
- 임계값(`NEAR_THRESHOLD`, `MIN_PUFFS` 등)을 바꿔 다시 돌려 보는 기능

핵심 로직은 6.1 평가 스크립트와 공유한다.

## 8. 개선 검토 중 🔧

모든 대책은 평가 스크립트(6.1)로 오탐과 미탐을 함께 확인한 뒤 적용 여부를 결정한다.

### 8.1 물 마시기 오탐 (#39)

**현상**: 물 마시는 영상(30fps, 약 21초)에서 이벤트가 확정됐다.

**원인**
1. 마시는 동작이 1.7~2.1초씩 3번 유지되어 puff 3회로 인정 → 흡연 의심
2. 연기가 없는데 smoke가 167회 중 89회 검출(최고 0.67). cigarette는 3회(최고 0.46)
3. motion = 1.0이면 √(smoke × 1.0)이라 smoke 0.25만으로도 0.5를 넘는다 — 마시기와 흡연을
   구분하지 못하는 신호(모션)가 약한 객체 신호를 끌어올리는 구조

**검토 중인 대책**
- 모션과 짝지을 때 객체 신호에 최소 신뢰도 기준 두기
- smoke + 모션 조합의 가중치를 cigarette + 모션보다 낮추기 (smoke는 김·수증기에도 반응)
- **모션은 관문으로만 사용**: 2차 확인을 할지만 정하고 combined 점수를 올리지 않게 한다. 확정은
  객체 증거의 세기로만 판단
- **객체 검출 위치 조건**: 담배·연기 박스가 손목 또는 입 추정 위치 근처일 때만 인정. 거리 기준은
  어깨너비로 정규화한 상수
- 데이터: 컵·물병·음료를 마시는 장면을 부정 샘플로 학습 셋에 추가

**v5 이후 확인된 내용** (2026-10-27): v5(마시는 장면 부정 샘플 약 200장 포함)에서는 smoke 오검출이
사라졌지만, 손에 든 물병을 cigarette로 오검출한다(최고 0.88). 박스 위치를 재 보니 drink 오검출은
입 근처가 3%뿐이고 손 쪽에 몰려 있었고, 흡연 영상의 검출은 61~84%가 입 근처였다. 그래서 위치
조건은 **"입 근처만 인정"** 쪽이 유효해 보인다(손목 근처까지 인정하면 걸러지지 않는다). 부정 샘플에는
"입에 댄 순간"뿐 아니라 "손에 들고 있는 상태"도 필요해 보인다.

### 8.2 2차 확인 크롭 축소 (#34)

사람 bbox 전체를 크롭하면 배경이 섞여 오검출이 난다(배경 금속 봉을 담배로 0.88 검출).
크롭 범위를 입 추정 위치 + 손목 기준(어깨너비 비례 마진)으로 좁히고, 손목이 안 보이면 입 주변으로
폴백한다. 8.1의 위치 조건과 같은 방향의 대책이다.

### 8.3 주기 샘플링이 고신뢰도 검출을 건너뜀 (#32)

1초 주기로 체크하면 순간적으로 높게 뜬 검출(예: cig 0.72)을 건너뛸 수 있다. 저프레임 영상에서
특히 심하다. 간격 축소, fps에 따른 동적 조정, 사전 필터 등을 검토 중이다.

### 8.4 2차 확인 병행 실행 ❓

**제안**: 사람이 감지되는 즉시 모션 판정과 담배·연기 검출을 병행한다(모션을 기다리지 않음).

**실험 결과** (v4, 포즈 640, 2026-10-27)

| 2차 확인 간격 | test4 | test5 | drink | 호출 수 (test5) | 처리 시간 (test5) |
|---|---|---|---|---|---|
| 1초 (현재) | 1명 확정 | 미확정 | 오탐 | 204회 | 21초 |
| 0.2초 | 미확정 | 미확정 | 오탐 | 875회 | 23초 |
| 매 프레임 | 미확정 | 미확정 | 오탐 | 5,661회 | 56초 |

- 자주 돌려도 흡연 감지는 늘지 않았고 오탐도 그대로였다. 연산량은 크게 늘었다.
- v4는 담배를 프레임마다 꾸준히 잡지 못한다. 표본이 많아지면 실제 검출률이 드러나 60% 비율에
  못 미친다. 병목은 실행 빈도가 아니라 모델 2의 프레임별 검출 안정성이다.

**결정 방법**: v5 모델로 같은 실험을 다시 돌려 결정한다. 병행으로 가면 8.1의 위치 조건을 함께
적용하고, 사람별 크롭 대신 전체 프레임 1회 추론 후 손목·입 위치로 사람에 배정하는 방식도
실험한다(연산량이 인원과 무관해지지만 작은 담배 검출이 더 어려워진다).

### 8.5 기타 확인된 한계

- 군중 장면의 사람 누락과 track id 전환 (3.1)
- 손을 입 근처에 계속 들고 피우는 경우 (3.2)
- 영상 파일 모드의 결과 요약이 종료 시점 기준 (4.1)

## 9. 서버·DB·대시보드 ❓

로드맵(소프트웨어 데모 버전)에서 **선택사항**으로 내려간 항목이다. 만든다면 기존 계획은
다음과 같다.

- FastAPI 이벤트 API: `POST /events`, `GET /events`, `POST /heartbeat`
- 저장소: SQLite. 메타데이터 `{시각, 지점 ID, 신뢰도}`만 저장하며 영상은 저장하지 않는다
- 대시보드: Streamlit — 시간대·요일 히트맵, 일별 감지 추이, 장치 상태

**논의된 내용**: 데이터 양이 적어(이벤트 하루 수십 건 수준) SQLite로 충분하며, PostgreSQL 전환은
여러 지점·외부 접속이 필요해질 때 검토한다. 테이블은 이벤트와 장치 상태 2개면 된다.
